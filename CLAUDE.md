# CLAUDE.md

Joey64: standalone Android N64 emulator for handhelds (Retroid, Odin, AYN, Anbernic), hosting the
mupen64plus-next libretro core from a Kotlin app with a C++ libretro frontend.

## Goals (priority order)
1. Automatic renderer + settings per game (ROM hash) and per device (GPU vendor/driver): parallel-RDP vs GLideN64.
2. Smooth frame pacing: Swappy, audio/video sync modes, big-core pinning, thermal fallback.
3. Handheld-first frontend: device detection, controller profiles, controller-only UI.

## Layout
- `app/src/main/java/com/joeysretro/joey64/` – Kotlin: `MainActivity` (surface/lifecycle), `NativeBridge` (JNI)
- `app/src/main/cpp/libretro_host.cpp` – dlopen core, environment callbacks, run thread, input state
- `app/src/main/cpp/egl_context.*` – EGL/GLES3 context, FBO the core renders into, 4:3 blit
- `app/src/main/cpp/vk_context.*` – Vulkan frontend for parallel-RDP: instance, swapchain, 4:3 blit of the core's image; the core creates the device via the v1 negotiation interface (creating it ourselves crashes Granite)
- `app/src/main/cpp/third_party/libadrenotools/` – BSD-2, copied from dolphin's checkout; loads custom Vulkan drivers (Turnip). Its hook libs ship in the APK and are found via nativeLibraryDir
- `app/src/main/assets/drivers/` – bundled Vulkan drivers (not committed, `*.so`): `libvulkan_freedreno.so` (Turnip Gen8 V38, StevenMXZ) and `faux123/libvulkan_freedreno.so` (Turnip faux123 v1.2.7, the Duo's Adreno 722; since 2026-11-06, same speed as v1.2.5, Duo compat 82/82). Sources, tags and md5s in `devtools/drivers/bundled.json`; `python devtools/check-drivers.py` reports newer releases. Licenses in `assets/licenses/`. Without them the app runs on the system driver
- `app/src/main/cpp/audio_out.*` – AAudio float at device rate + linear resampler + SPSC ring (blocking write = audio sync)
- `app/src/main/jniLibs/arm64-v8a/` – the core `libjoey64_libretro_android.so` (not committed; older test builds used upstream's `libmupen64plus_next_libretro_android.so`, which the app still finds). Put it there with `devtools/bundle-core.sh [libretro.so]`, which also writes `core-version.txt` (committed: core branch, commit, uncommitted files, md5), so the app's history says which core each build shipped
- Core source: `C:\GithubProjects\joey64-core` (private repo JoeysRetroHandhelds/joey64-core, branch `handheld`; `upstream` = libretro/mupen64plus-libretro-nx). Build (Git Bash, NDK 27.3):
  `ndk-build.cmd -C libretro/jni APP_ABI=arm64-v8a GLES3=1 STRINGS=<ndk>/toolchains/llvm/prebuilt/windows-x86_64/bin/llvm-strings.exe AWK=awk TR=tr -j16`.
  On a clean tree the asm_defines rule fails under cmd.exe: run `llvm-strings <obj of asm_defines.c> | tr -d '' | awk -v dest_dir=libretro/obj/local/arm64-v8a/asm_defines/ -f mupen64plus-core/tools/gen_asm_defines.awk` and rerun. Output `libretro/libs/arm64-v8a/libretro.so` → copy to jniLibs under the name above

## Build / run
- Android Studio or `./gradlew assembleDebug` (needs JDK 17+, e.g. Android Studio's `jbr` as JAVA_HOME)
- arm64-v8a only, minSdk 29, NDK 27.3
- Dev ROM path: `/sdcard/Android/data/com.joeysretro.joey64/files/test.z64`; or put ROMs in `files/roms/` (internal via run-as on the Flip) and start with `--es rom "<file name>"`, which also names the save
- Logs: `adb logcat -s joey64host core Granite`
- Session logs (for testers, 2026-11-06): each process start writes `files/logs/<yyyyMMdd-HHmmss>-<pid>-app.log` (every line the app, host and core log, through `joeylog.cpp`, so the Duo's logd filter, which drops all info lines, doesn't matter; opens with a header: build commit, bundled core, device/SoC, Android, CPU, memory, battery/heat, display, intent, the previous exit; then GPU/driver, ROM header/CRCs, options in effect, stats), `-system.log` (logcat for our pid), and `-exit-*.txt` plus `.trace` / `.tombstone.pb` for earlier runs' ends as Android recorded them (ApplicationExitInfo: crash, native crash with symbolized stacks, ANR). Last 5 sessions kept (`LogFiles.kt`). Debug builds: `adb shell am broadcast -a com.joeysretro.joey64.LOGS` zips them to `cache/joey64-logs.zip`; the Share button waits for Joey's menus. Kotlin logs through `JLog`, native through `LOGI`/`LOGE` (`joeyLog`), never `Log.*` / `__android_log_print` directly
- Driver by GPU (`MainActivity.setupGpu`, logged as `GPU: ...`): bundled faux123 Turnip on the Adreno 722 (Duo: draws Mario Party 2's text boxes right, 82/82 compat), bundled Turnip Gen8 on other Adreno 6xx–8xx (verified on Adreno 740), the system driver on Mali. malisx2 (bmdhacks/malisx2 + the Mesa patches in its `patches/mesa/`) is not bundled: ~14% slower than stock on the Mali-G52, and no device we have lacks a Vulkan 1.1 driver; it can still be dropped in as a dev driver. A custom driver that has no usable GPU falls back to the system driver. Override with `--es driver system|turnip|faux123`
- Custom Vulkan driver (dev): a `.so` in `/sdcard/Android/data/com.joeysretro.joey64/files/drivers/` (or internal `files/drivers/`) overrides the choice; the app copies it to internal storage and loads it. From Git Bash set `MSYS_NO_PATHCONV=1` or adb paths get mangled
- Renderer: parallel-RDP when the driver in use is a custom one or stock Mali with Vulkan 1.1 and the GPU has 16-bit storage buffers (the Adreno 610 has none: GLideN64), else GLideN64; override with `--es renderer parallel|gliden64` on `am start`
- Dev process env (read by the core): `--es env "PARALLEL_RDP_SMALL_TYPES=0,KEY=value"`
- Controls (Phase 4, `controls/` + `launcher/screens/ControlsScreen.kt`): four players, each with a controller (built in, a pad by `InputDevice` descriptor, or None) and its own buttons, stick, dead zone and pak, in `files/controls/` (`all.json`, `games/<save name>.json`, `hotkeys.json`). MainActivity gives each event to its controller's player (`PlayerInput` per port; a new pad goes to the first player with None, Auto mapped), the host keeps buttons and sticks per port and plugs in only players with a controller (`setPortsPresent`, also between frames). The core runs with `mupen64plus-alt-map` (each N64 button its own RetroPad bit) and its dead zone off (ours is round). Auto pak: the Rumble Pak for the games in `assets/pakdb.tsv` (`devtools/make-pakdb.py` from the core's mupen64plus.ini), the Controller Pak for the rest; the launcher passes the MD5 (`EXTRA_MD5`). New pads: Auto map's table (`controls/AutoMap.kt`, `docs/n64-controllers.md`), else by position (bottom = N64 A, left = N64 B, L2 = Z, right stick = C; the AYN pad 2020:0111, which reports itself external, has Nintendo labels and counts as built in). Presses shorter than a frame are held for 4 polls (Snap ignores 1-frame presses). R3 toggles fast-forward (no on-screen button for now) (4x cap, audio muted, ~60 fps shown, async parallel-RDP and 1x upscaling while on; the core rebuilds its renderer between frames, Odin 3 at 4x: 81 -> 240 fps in Peach's Fury, 62 -> 240 in GoldenEye; `--es env N64_FF_KEEP_UPSCALE=1` keeps the upscale)
- Dev core options: `--es opts "key=value,key=value"` on `am start`; GameShark codes: `--es cheats '<code>;<code>'` (quote the whole `am start` for `adb shell`, or the device shell splits at spaces)
- Debug builds: `adb shell am broadcast -a com.joeysretro.joey64.DUMP --es name x` writes RDRAM to `files/dumps/x.bin`
- Save RAM: `files/saves/<ROM file name without extension>.srm`, as RetroArch names them (a .zip/.7z ROM, unpacked by RomFiles.kt: the archive's name, as RetroArch does, not the file inside) (its Mupen64Plus-Next .srm files work as they are; import = copy them in). Written atomically every 120 frames when changed, on pause and on exit. A ROM without a name (the `test.z64` dev path) uses `<fnv64 of ROM>.srm`, which is also read as a fallback when the named save doesn't exist yet
- Save states (Phase 3, `states/`): `files/states/<save name>.state` (Slot 1), `.state1`-`.state9`, `.state.auto`, in RetroArch's format (RZIP + RASTATE around the core's `M64+SAVE` data, `StateFormat.kt`). The host takes/loads the core's state between frames (`NativeBridge.saveState`/`loadState`, also while paused). Quit to library (pause menu, or hotkey) writes the auto slot; the launcher's Continue passes `--es com.joeysretro.joey64.LOAD_STATE auto` (or `recovery`). A recovery state goes to `files/recovery/` every 2 min while playing and is deleted on a clean quit. The core (since 0044899) refuses data that isn't `M64+SAVE` or is from another ROM and keeps running (older cores leaked `savestates_lock` and hung the emulation thread)
- Library views (Phase 5, `launcher/library/LibraryViews.kt`, `screens/CollectionPopups.kt`, `screens/SearchScreen.kt`): the Filter button over the grid opens Show (All games, Favourites + the user's collections, filters 4 players / Hacks and translations / Never played); a game's options have Add to collection; Search is on the rail and Y. Favourites is `games.favorite`, collections are the V1 `collections`/`collection_games` tables (no schema change). 4 players reads `assets/n64-players.tsv` by the .z64 CRC32 (`devtools/make-players.py` from libretro-database metadat/maxusers); Hacks = MD5 not in the box-art table. On the Thor the soft keyboard opens on the bottom screen (JoeyOS's second-screen app holds it); `screencap -d <id>` from `dumpsys SurfaceFlinger --display-id` shows it
- Cheats (Phase 6, `cheats/`, `launcher/screens/CheatsScreen.kt`): lists from the `joey64-cheats` repo (local at `C:\GithubProjects\joey64-cheats`; public on GitHub as JoeysRetroHandhelds/joey64-cheats since 2026-11-07, the app downloads its `release` branch), fetched to `files/cheatlists/` by the header key `CRC1-CRC2-CC` (`games.header_key`, schema V4); debug builds read `files/dev_cheats_base` (serve `dist/` on the PC, `adb reverse tcp:8813 tcp:8813`, `http://127.0.0.1:8813/`). What's on lives in the data folder's `cheats/<save name>.json`; MainActivity gives the core those codes before loadGame, and `NativeBridge.setCheats` replaces them between frames after the pause menu's Cheats. GameShark-button codes are hidden (the core never presses it)
- In-game UI (Phase 3): Back opens the pause menu (`GameOverlay` hosts `launcher/ingame/PauseScreens.kt`, one JoeyDialog that switches to the slot picker); pop-ups go to a non-focusable panel window top left (`InGamePopups.kt`). Hotkeys (Controls › Hotkeys, `hotkeys.json`): hold the hotkey button (Select by default) + R1 save, L1 load, Left/Right slot, Y screenshot (`files/screenshots/`), Start reset, B quit; Back alone the pause menu, R3 alone fast-forward. The pause menu's Controls opens the page over the paused game, set to that game (`InGameControls`, a full-screen JoeyDialog); changes apply when it closes. `NativeBridge.captureFrame` reads the frame back (both renderers), `resetGame` is `retro_reset`; both between frames. Dev: `--es env N64_POPUP_TEST=1` keeps a pop-up on screen. On adb, hold combos with `input -d 0 keycombination KEYCODE_BUTTON_SELECT KEYCODE_BUTTON_R1`
- Debug builds: `adb shell am broadcast -a com.joeysretro.joey64.STICK --ei x 0 --ei y 32767 --ei ms 200` moves the stick (`--ei stick 1` = C stick)
- Never set `MSYS_NO_PATHCONV=1` for `./gradlew`: the native build silently does nothing

## Conventions
- Core options are overridden in `g_optionOverrides` (libretro_host.cpp); M3 replaces this with the profile DB.
- Per-game facts live in `gamedb/games.json` (rules: `gamedb/README.md`): any change to a game's status (problem found, fixed, regressed, game-specific setting added or dropped) updates it in the same commit.
- Emulation runs on one native thread that owns the GL context; UI thread only posts surface/input changes.
- License: GPL-3.0-or-later (`LICENSE`; README "Licensing" says why). GPLv3 code may be copied, GPLv2-only code (Project64) may not. ares-derived code keeps its ISC notice.
- M0 verified on AYN Thor (SD 8 Gen 2): SM64 at 60 fps on GLideN64. `adb logcat -s joey64host` prints fps stats every 5 s.

## Known issues
- parallel-RDP on AYN Thor with the stock Adreno 740 driver (676.53): black screen, the compiler fails on a parallel-RDP compute shader. Fixed by Turnip ("Turnip Gen8 V38", Mesa 26.99.99 / Vulkan 1.4.363): renders correctly at 60 fps.
- Synchronous parallel-RDP (needed for CPU framebuffer reads, e.g. Snap photos) costs ~10 ms/frame in Snap on the Thor (async: ~2–4 ms; GLideN64: 2.5 ms). On Adreno/Turnip, parallel-RDP runs synchronous by default (`MainActivity`): async there breaks Yoshi's Story, Resident Evil 2, Cruis'n USA (black), New Tetris (halts) and Snap, also in upstream's async code, while sync costs ~1-2 ms and no fps on the Odin 3/Duo. On Mali (Flip) sync costs up to a third of the frame rate, so it stays async except games in `kSyncRdpGames` (libretro_host.cpp, by header game code: Snap = NPF). Synchronous only outside fast-forward. `--es opts mupen64plus-parallel-rdp-synchronous=True|False` overrides.
- Smart parallel-RDP sync (core `gliden64-update`): stands in for synchronous mode (`--es env N64_RDP_SMART=0` gives plain sync). parallel-RDP runs async, remembers the RDRAM pages it drew into, and at each SyncFull mprotects them; the first CPU access faults, waits for the GPU and unlocks them (gopher64's idea, done with page protection). Neither the Duo's Turnip nor the Flip's Mali has VK_EXT_external_memory_host, so parallel-RDP copies results back on a worker thread; the core maps RDRAM from a memfd twice and gives parallel-RDP the second, never-protected view (`g_rdram_alias`). Measured: Duo renders RE2 and Cruis'n USA like sync (async shows them black) at or below sync cost; Flip Snap 14.4 -> 5.0 ms/frame vs sync. Most games touch drawn pages every frame (Flip: SM64 587, OoT 599 waits per 600 SyncFulls), so it is no faster than sync for them; on by default everywhere it cost the Flip ~20 fps in SM64/OoT/Banjo against async, so Mali stays async except `kSyncRdpGames`. The log line `smart sync: N CPU waits in the last 600 SyncFulls` shows how often a game reads back what the RDP drew. Precise mode (default since core 92fe5c3, `N64_RDP_SMART_PRECISE=0` turns it off) also tracks the drawn byte ranges: a dynarec load/store (PC in new_dynarec's code cache) whose 8 bytes miss them opens only its page without waiting, and a helper thread relocks it 0.5 ms later; copies (DMA, RSP, C memcpy) always wait, since they fault only on their first byte (letting them through left Cruis'n USA stuck). Portal +11.9% over page-level smart sync, Duo compat 82/82. `N64_RDP_SMART_DEBUG=1` logs inside / copy / shared-page fault counts
- Early acquire on Mali (default since 2026-11-05, MainActivity sets `N64_EARLY_ACQUIRE=30` unless `--es env` does): with repeat frames skipped, after 30 new frames in a row the next frame acquires its swapchain image at frame start, so a blocking acquire waits before the input poll (Flip Smash poll->display 58 -> ~40 ms). Off on Adreno: no gain on the Duo, Odin 3 or Portal, GoldenEye judders on the Duo. Flip compat 82/82
- Single-threaded RDP commands on Mali (default since 2026-11-06, MainActivity sets `PARALLEL_RDP_SINGLE_THREADED_COMMAND=1` unless `--es env` does): parallel-RDP processes commands on the emulation thread, not a worker ring. Flip +3.7% uncapped, none slower, compat 82/82. Adreno keeps the ring (Duo mixed)
- Repeat frames (default since core 92fe5c3 / app 07869ad): the core skips scanning out a refresh when the VI registers match, the RDP drew nothing into the scanned rows and their RDRAM hash matches; the Vulkan side then acquires and presents nothing for it. Portal +21.5%, Flip +14.7% uncapped. `N64_RDP_SKIP_DUP=0` (core) and `N64_SKIP_DUPES=0` (app) turn it off; `N64_RDP_SKIP_DUP_DEBUG=1` logs the detection
- CPU core: the dynamic recompiler, except `kInterpreterGames` (cached interpreter): Sin and Punishment (English patch) jumps to a bogus address after boot since upstream's 3.0 core update.
- ROM hacks that DMA from odd cartridge addresses (SM64 Last Impact: MIO0 data one byte off, then the decompressor overwrites its own code; Star Road Deluxe: collision data one byte off, NULL pointer) crash in every upstream libretro build: hardware and upstream ignore bit 0 of the PI cart address. The core (joey64-core `gliden64-update`) now follows M64Plus FZ: ROMs missing from mupen64plus.ini keep bit 0, ROMs in it align unless their entry says `ForceAlignmentOfPiDma=0` (FZ's six SM64-hack entries copied). Both run on parallel-RDP (Odin 3 60 fps; Flip: Last Impact 60, Star Road 35-40 in-game)
- ROMs missing from mupen64plus.ini (hacks, randomizers, translations) take their save type from the header game ID (core `rom.c`, lists from ares, ISC); before, they all got EEPROM 4K, so hacks of 16K EEPROM games (DK64, Banjo-Tooie, Yoshi's Story) could not save. SRAM/FlashRAM were already auto-detected by the cart on first access
- Display lag: the core used to scan out (and end the libretro frame) at the VI interrupt, before the game's handler set the new VI_ORIGIN, so every frame was shown one frame late. It now scans out at the active picture start (`VI_SCANOUT_EVT`, about 1 ms after the origin write on SM64/MK64/OoT instead of 17 ms): ~16 ms less lag, same speed. `--es env N64_SCANOUT_AT_VI=1` restores the old timing
- AAudio low-latency path is denied on the Thor (output has no RAW flag).
- AAudio asks for an exclusive (MMAP) stream by default: device latency Duo 14-16 -> 10 ms, Odin 3 14 -> 9 ms, no underruns or fps cost; the Flip refuses it and AAudio falls back to shared (`sharing 1` in the log line). `--es env N64_AUDIO_EXCLUSIVE=0` forces shared
- Audio sync waits before each frame (`AudioOut::waitForRoom`) while more than target + one frame is queued (target starts at 20 ms, +10 ms per 5 s window with underruns at full speed, max 150 ms). Rate control (max 1%) holds the fill at the target when vsync paces instead, and stays neutral while audio paces. The stats line shows fill/target, underruns and `poll->display` (input poll to scanout, from VK_GOOGLE_display_timing). Measured: Portal 35 ms queued, Flip adapts to ~70 ms, no underruns at full speed (was a full ~200 ms ring); poll->display unchanged (Portal 18.5 ms, Flip 28 ms in a match). AAudio's own buffer starts at 2 bursts (default was its full 8-burst capacity) and grows a burst per xrun; `device` in the stats is written-to-played: Portal 55 -> 31 ms, Flip 70 -> 37 ms. Total audio latency Portal ~255 -> ~66 ms, Flip ~270 -> ~105 ms.
- Pokémon Snap on GLideN64 needs the source-built core (joey64-core `handheld`, commits 1988dcc + a1accf3): upstream greys out Oak's Mark because the selection screen's visibility check copies depth-buffer strips, and GLideN64 served its color buffer instead. The same commit fixes glsm hiding all GL extensions on GLES3 builds. Worth upstreaming.
- 120 Hz panels (Portal, Duo, Odin 3) with 60 fps games: by default each frame is presented once, as soon as it's ready (like RetroArch's default), so 5-19% of frames show for 1 or 3 refreshes instead of 2 (Odin 3 at 4x: ~90%). `--es env N64_SWAP_INTERVAL=1` presents each frame twice (RetroArch's swap interval 2): no judder, +8-16 ms poll->display. `N64_SWAP_INTERVAL=2` is timed pacing (`VkContext::paceFrame`): one present per frame with a `desiredPresentTime` on an even vsync, frames started just in time; 0-5% uneven for +2-7 ms (Portal ~20 -> ~24 ms, Duo ~23 -> ~27-33 ms, Odin 3 ~20 -> ~23 ms). Both opt-in. No VRR on any of these devices
- The activity handles every config change itself (`configChanges` in the manifest), so dark mode, font size, dock or keyboard changes no longer restart the game (verified on the Duo: same process through a dark-mode and font-scale flip). Also `appCategory="game"` and `preferMinimalPostProcessing`
- Benchmarking (dev env): `N64_BENCH=1` runs uncapped (no speed cap, vsync off, audio dropped, settings unchanged; repeat frames are still skipped unless `N64_SKIP_DUPES=0`), so the counter shows the headroom a full-speed game has; `N64_STATE=<raw save state path>` loads a state 30 frames after boot. RetroArch states must be unpacked to the core's `M64+SAVE` data (RZIP, then the MEM chunk of RetroArch's RASTATE container). Compare changes as uncapped fps from fixed states across several games, variants alternating
- Experiments, off by default (`--es env`): `N64_PERF_HINT=1` (ADPF performance hint session for the emu thread; Odin 3: same medians, slightly lower worst frames), `N64_GPU_TURBO=2` (KGSL clock pin, kept for the Portal slow-mode check; mode 1, adrenotools max clocks, removed 2026-11-05: no gain), core `N64_DRC_STATS=1` (dynarec compile time every ~5 s)
- The swapchain is rebuilt on `surfaceChanged`: it is created before the system bars hide, and Android only reports SUBOPTIMAL (ignored), so it stayed 1920x969 and the picture was stretched
- Duo (Adreno 722): parallel-RDP at 4x/8x drops geometry (invisible characters, flicker) with the bundled Turnip and Turnip-Duo v5.1; 1x/2x are fine, so `MainActivity.capUpscaling` caps it at 2x. The Odin 3 (Adreno 830) and Portal are fine at 4x. The Duo's logd drops logs below ERROR: `--es env N64_LOG_ERR=1` logs at ERROR
- Tried and dropped for input latency: pre-rotating the swapchain (no change on Portal or Duo); the shared present mode (front buffer, offered only by the Flip's Mali driver, not Turnip): continuous refresh shudders even when copies are synced to Choreographer vsync, demand refresh and the synced copy drop the Flip to 24-52 fps
