# CLAUDE.md

Joey64: standalone Android N64 emulator for handhelds (Retroid, Odin, AYN, Anbernic), hosting the
mupen64plus-next libretro core from a Kotlin app with a C++ libretro frontend.

## Goals (priority order)
1. Automatic renderer + settings per game (ROM hash) and per device (GPU vendor/driver): parallel-RDP vs GLideN64.
2. Smooth frame pacing: Swappy, audio/video sync modes, big-core pinning, thermal fallback.
3. Handheld-first frontend: device detection, controller profiles, controller-only UI.

## Layout
- `app/src/main/java/com/joeysretro/joey64/` – Kotlin: `MainActivity` (surface/lifecycle), `NativeBridge` (JNI)
- `app/src/main/cpp/libretro_host.cpp` – dlopen core, environment callbacks, run thread, input state
- `app/src/main/cpp/egl_context.*` – EGL/GLES3 context, FBO the core renders into, blit to the window at Settings › Video's shape (`display_opts.h`), or its colour/sharpening shaders
- `app/src/main/cpp/vk_context.*` – Vulkan frontend for parallel-RDP: instance, swapchain, blit of the core's image at Settings › Video's shape (or `vk_post.*`, the colour/sharpening compute pass); the core creates the device via the v1 negotiation interface (creating it ourselves crashes Granite)
- `app/src/main/cpp/third_party/libadrenotools/` – BSD-2, copied from dolphin's checkout; loads custom Vulkan drivers (Turnip). Its hook libs ship in the APK and are found via nativeLibraryDir
- `app/src/main/assets/drivers/` – bundled Vulkan drivers (not committed, `*.so`): `libvulkan_freedreno.so` (Turnip Gen8 V38, StevenMXZ) and `faux123/libvulkan_freedreno.so` (Turnip faux123 v1.2.7, the Duo's Adreno 722; since 2026-11-06, same speed as v1.2.5, Duo compat 82/82). Sources, tags and md5s in `devtools/drivers/bundled.json`; `python devtools/check-drivers.py` reports newer releases. Licenses in `assets/licenses/`. Without them the app runs on the system driver
- `app/src/main/cpp/audio_out.*` – AAudio float at device rate + linear resampler + SPSC ring (blocking write = audio sync)
- `app/src/main/jniLibs/arm64-v8a/` – the core `libjoey64_libretro_android.so` (not committed; older test builds used upstream's `libmupen64plus_next_libretro_android.so`, which the app still finds). Put it there with `devtools/bundle-core.sh [libretro.so]`, which also writes `core-version.txt` (committed: core branch, commit, uncommitted files, md5), so the app's history says which core each build shipped
- Core source: `C:\GithubProjects\joey64-core` (private repo JoeysRetroHandhelds/joey64-core, branch `handheld`; `upstream` = libretro/mupen64plus-libretro-nx). Build (Git Bash, NDK 27.3):
  `ndk-build.cmd -C libretro/jni APP_ABI=arm64-v8a GLES3=1 STRINGS=<ndk>/toolchains/llvm/prebuilt/windows-x86_64/bin/llvm-strings.exe AWK=awk TR=tr -j16`.
  On a clean tree the asm_defines rule fails under cmd.exe: run `llvm-strings <obj of asm_defines.c> | tr -d '' | awk -v dest_dir=libretro/obj/local/arm64-v8a/asm_defines/ -f mupen64plus-core/tools/gen_asm_defines.awk` and rerun. Output `libretro/libs/arm64-v8a/libretro.so` → copy to jniLibs under the name above

## Build / run
- Android Studio or `./gradlew assembleDebug` (needs JDK 17+, e.g. Android Studio's `jbr` as JAVA_HOME)
- arm64-v8a only, minSdk 29, NDK 27.3
- Dev ROM path: `/sdcard/Android/data/com.joeysretro.joey64/files/test.z64`; or put ROMs in `files/roms/` (internal via run-as on the Flip) and start with `--es rom "<file name>"`, which also names the save
- Logs: `adb logcat -s joey64host core Granite`
- Session logs (for testers, 2026-11-06): each process start writes `files/logs/<yyyyMMdd-HHmmss>-<pid>-app.log` (every line the app, host and core log, through `joeylog.cpp`, so the Duo's logd filter, which drops all info lines, doesn't matter; opens with a header: build commit, bundled core, device/SoC, Android, CPU, memory, battery/heat, display, intent, the previous exit; then GPU/driver, ROM header/CRCs, options in effect, stats), `-system.log` (logcat for our pid), and `-exit-*.txt` plus `.trace` / `.tombstone.pb` for earlier runs' ends as Android recorded them (ApplicationExitInfo: crash, native crash with symbolized stacks, ANR). Last 5 sessions kept (`LogFiles.kt`). Debug builds: `adb shell am broadcast -a com.joeysretro.joey64.LOGS` zips them to `cache/joey64-logs.zip`; the Share button waits for Joey's menus. Kotlin logs through `JLog`, native through `LOGI`/`LOGE` (`joeyLog`), never `Log.*` / `__android_log_print` directly
- Driver by GPU (`MainActivity.setupGpu`, logged as `GPU: ...`): bundled faux123 Turnip on the Adreno 722 (Duo: draws Mario Party 2's text boxes right, 82/82 compat), bundled Turnip Gen8 on other Adreno 6xx–8xx (verified on Adreno 740), the system driver on Mali. malisx2 (bmdhacks/malisx2 + the Mesa patches in its `patches/mesa/`) is not bundled: ~14% slower than stock on the Mali-G52, and no device we have lacks a Vulkan 1.1 driver; it can still be dropped in as a dev driver. A custom driver that has no usable GPU falls back to the system driver. Override with `--es driver system|turnip|faux123`
- Custom Vulkan driver (dev): a `.so` in `/sdcard/Android/data/com.joeysretro.joey64/files/drivers/` (or internal `files/drivers/`) overrides the choice; the app copies it to internal storage and loads it. From Git Bash set `MSYS_NO_PATHCONV=1` or adb paths get mangled
- Renderer: parallel-RDP when the driver in use is a custom one or stock Mali with Vulkan 1.1 and the GPU has 16-bit storage buffers (the Adreno 610 has none: GLideN64), else GLideN64; stock Mali on a CPU with only little cores (A53/A55, e.g. the RK3566: `GpuRules.littleCoresOnly`) gets GLideN64 (2026-11-09, parallel-RDP held full speed in no game there); a game in `GpuRules.gameRenderer` (by ROM MD5: SM64 Last Impact, 2026-11-09) gets GLideN64 + HLE where Auto would give parallel-RDP; override with `--es renderer parallel|gliden64` on `am start`
- Dev process env (read by the core): `--es env "PARALLEL_RDP_SMALL_TYPES=0,KEY=value"`
- Controls (Phase 4, `controls/` + `launcher/screens/ControlsScreen.kt`): four players, each with a controller (built in, a pad by `InputDevice` descriptor, or None) and its own buttons, stick, dead zone and pak, in `files/controls/` (`all.json`, `games/<save name>.json`, `hotkeys.json`). MainActivity gives each event to its controller's player (`PlayerInput` per port; a new pad goes to the first player with None, Auto mapped), the host keeps buttons and sticks per port and plugs in only players with a controller (`setPortsPresent`, also between frames). The core runs with `mupen64plus-alt-map` (each N64 button its own RetroPad bit) and its dead zone off (ours is round). Rumble (players 1-4 since 2026-11-07; the host refused ports 2-4 before): the host keeps each port's motor and `waitRumble` hands MainActivity a 4-bit mask; each player vibrates their own pad when it has a motor, the player with the built-in controls vibrates the device, and so does player 1 when no player has the built-in controls. Auto pak: the Rumble Pak for the games in `assets/pakdb.tsv` (`devtools/make-pakdb.py` from the core's mupen64plus.ini), the Controller Pak for the rest; the launcher passes the MD5 (`EXTRA_MD5`). New pads: Auto map's table (`controls/AutoMap.kt`, `docs/n64-controllers.md`), else by position (bottom = N64 A, left = N64 B, L2 = Z, right stick = C; the AYN pad 2020:0111, which reports itself external, has Nintendo labels and counts as built in). Presses shorter than a frame are held for 4 polls (Snap ignores 1-frame presses). Stick feel (approved mockup 2026-11-07; `controls/StickFeel.kt`, `launcher/screens/StickFeelPopup.kt`): a row under Dead zone opens a popup with Range (50-150%), Response curve (Linear, Precise t^1.8, Quick t^0.6), Octagon gate (full diagonals 70, 70 as an N64 stick, against a circle's 57, 57), Invert, Swap, Anti-dead zone (0-30%) and Trigger threshold (analog L2/R2, default 50%), each per player and per game, with a live preview (the popup takes the stick moves; the D-pad moves between rows). `StickFeel.apply` gives the N64 stick with 1 = 80, up to 1.5; the core runs at `mupen64plus-astick-sensitivity` 150, so the host sends v / 1.5 (`PlayerInput.toRetroStick`). The Stick row also has Left stick and D-pad (the D-pad moves the stick at full tilt while held); with either D-pad choice the D-pad no longer presses the N64 D-pad. On adb, `input joystick motionevent MOVE <x> <y>` moves AXIS_X/Y for the preview Fast-forward: hotkey button + R2 by default (since 2026-11-07, was R3 on its own; hotkeys.json version 3 moves the old saved defaults: R3 fast-forward, + Start reset, + B quit), no on-screen button. Its popup (Controls › Hotkeys) sets Mode: Toggle, Hold (while held) or Adaptive (held, speed follows the trigger's depth from normal up to the top speed; the game doesn't see that trigger meanwhile; on a button without pressure it works like Hold), and Speed 125-400% (`NativeBridge.setFastForwardSpeed`; the thermal cap still applies) (sound as Settings › Audio's Fast-forward sound says, muted by default; ~60 fps shown, async parallel-RDP and 1x upscaling while on; the core rebuilds its renderer between frames, Odin 3 at 4x: 81 -> 240 fps in Peach's Fury, 62 -> 240 in GoldenEye; `--es env N64_FF_KEEP_UPSCALE=1` keeps the upscale). Slow motion and Rewind (approved mockup 2026-11-08, scratchpad build_slowrw.py / slowrw_mock.png, "Approve as drawn"), Controls › Hotkeys under Fast-forward, each with its own popup. Slow motion: not set by default, Toggle or Hold, Speed 20-90% (default 50%); the host's speed cap runs at that speed without the audio wait, and its sound goes through `AudioOut::writeFast` slower and lower, as Settings › Audio's Fast-forward sound says; fast-forward ends it; a pop-up stays while it's on. Rewind: hotkey button + L2, held; Rewind Off by default (the popup's On records while playing), How far back 10 s-5 min (default 1 min), Steps every 1/2/4 frames (default 2), and a memory line (80 KB a moment). The host (`rewind.h`) takes the state every Steps frames, a worker keeps the newest whole and each older moment as the XOR to the next one (runs of equal 8-byte words, the rest deflated at level 1) with the achievements' progress; held, one moment every Steps frames is loaded and one frame run from it (about normal speed, no sound, no achievement checks), and letting go carries on from there (achievements from that moment's progress). A loaded state or Reset starts the recording over. Pop-ups: Rewinding N s back with a bar, Can't go further back, Rewind is off; Not in Hardcore for both once Hardcore exists (`RaHardcore`). The log line `rewind: N moments kept` every 10 s has the costs. A moment's achievements' progress is packed the same way, as the XOR to the next newer moment's (a loaded set's is hundreds of KB: SM64's three sets 445 KB; kept whole, 1 min held 860 MB, now 96 MB, Thor 2026-11-08). Thor 2026-11-08 (results/srw1-srw4): a moment takes 2.5-4.1 ms to take and 2.5-5.2 ms to pack, 15-82 KB (SM64 16, GoldenEye 62, Conker 80; 1 min at every 2 frames about 30-145 MB), never skipped; 5 s held goes back 300 frames; parallel-RDP 1x and 4x, GLideN64, and a hold to the oldest moment (Can't go further back) all work; slow motion 50% runs at 30 fps, with Full sound the ring holds 21/20 ms (2 underruns per 5 s). Underruns in and right after rewind or slow motion don't grow the audio latency target (`g_audioRefillWindows`)
- Settings › Emulation (approved mockup 2026-11-08, scratchpad build_emu.py; `emulation/EmulationSettings.kt`, `launcher/screens/EmulationTab.kt`): a tab after Video, All games or one game like Video, in `files/emulation/` (`all.json`, `games/<save name>.json`; Game settings has it as a part between Video and Audio). Every row applies when the game next starts (MainActivity `emuAtStart`, read in onCreate; `EmuApply`). Overclock: Auto sets nothing (the host's smoother timing and a 60 fps code's CountPerOp=1 still apply), Normal = `mupen64plus-CountPerOp` 0 (the core's ROM database, else 2), 2x = 1, 4x = 1 with `CountPerOpDenomPot` 1; any of them turns off the 60 fps code's speed-up. CPU core: Auto sets nothing (the host picks the recompiler for every game), Recompiler / Interpreter set `mupen64plus-cpucore` (dynamic_recompiler / cached_interpreter). Expansion Pak: set for one game only (greyed on All games); Off = `mupen64plus-ForceDisableExtraMem`, never applied to a game in `ExpansionPak.NEEDED_BY` (DK64, Majora's Mask, Perfect Dark by game code; the row says "Needed by this game"). Thermal fallback (`N64_THERMAL_GOV=1`), moved from Video: `EmuStore` moves any Video file's "thermal" over when it opens (LauncherActivity and MainActivity open it first). The popups' "Auto gives ..." line copies the host's lists (`EmuAuto`, checked against libretro_host.cpp by EmuSettingsTest) and the `device` pref `smoother` (whether this device got smoother timing at its last game start). `--es opts` still wins. Performance mode (Balanced / Max / Battery saver) was dropped (Joey 2026-11-08) after the Thor measurement showed no difference (README perf-hint item).
- Settings › Video (approved mockup 2026-11-07; `video/VideoSettings.kt`, `launcher/screens/VideoTab.kt`): All games or one game (the header chip, the same popups as Controls), in `files/video/` (`all.json`, `games/<save name>.json` holding only that game's own rows: a dot marks them, Y resets the row). MainActivity reads it in onCreate (`VideoStore.forGame(earlySaveName())`) and sets: Resolution (parallel-RDP upscaling, or GLideN64's native factor; the Duo's 2x cap still applies), the N64 filters and their Look presets (Original; Sharp = VI AA and bilinear off, with the sharp-bilinear blit; Sharper = dither filter off too), deinterlace, supersampling, native texture LOD and tex rect as core options; Renderer and Driver (Auto = by GPU as below; the dev extras still win, and what Auto picks goes to the `device` prefs for Auto's label: `auto_renderer`, and `driver` when the driver was left on Auto; `renderer` is the one that last ran); Frame pacing (Lowest lag; Steady = `N64_SWAP_INTERVAL=1`; Steady, less lag = 2), unless `--es env` sets it; Screen orientation; Fill the camera cutout. The host gets the rest (`display_opts.h`; `NativeBridge.setDisplay`, `setColour`, `setSharpen`): Aspect ratio (Auto = 4:3, or the widescreen code's shape when Widescreen is on; 4:3, 16:9, Stretch), Integer scaling, Black frame insertion (Vulkan: the spare refresh on a 120 Hz screen is presented black; Thor poll->display 51 against 38-41 ms), Colour (brightness, contrast, saturation, gamma) and Sharpening (CAS or FSR 1, with a strength). Colour and sharpening are shaders that run only while one is changed: Vulkan compute (`vk_post.cpp`, `shaders/post_*.comp`) and GLES fragment (`shaders/post_gl.frag`, in `egl_context.cpp`), with AMD FidelityFX CAS and FSR 1 (MIT, `third_party/ffx/`). `sh devtools/build-shaders.sh` rebuilds `shaders/post_spv.h` and `shaders/post_gl.h` (both committed) and checks the GLES ones as GLSL ES. Measured on the Thor, both renderers: 60 fps, and the same poll->display with any of them. Screenshots and state pictures keep the raw picture
- Settings › Audio (approved mockup 2026-11-07; `audio/AudioSettings.kt`, `launcher/screens/AudioTab.kt`): All games or one game (the header chip, as Video), in `files/audio/` (`all.json`, `games/<save name>.json`). A game can only have its own Volume and Latency; its other rows are greyed. MainActivity reads it before loadGame (`applyAudio`) and calls `NativeBridge.setAudio`. Volume (0-100%, gain = (v/100)^2), Mute and Mono are applied in the AAudio callback (`AudioOut::setMix`). Latency, read when the stream opens: Auto = the adaptive target (20 ms, grows to 150), Low = 10 ms that never grows (on the Thor it crackles all the time, 10-22 underruns per 5 s), Safe = 60 ms, grows. Fast-forward sound: Mute (as before), Quieter (a quarter of the gain, half the loudness), Full. Its sound goes through `AudioOut::writeFast`, which doesn't block: it resamples at the fast-forward speed (pitch goes up), steered by the ring's fill, and drops what doesn't fit. Thor at 240 fps: fill 22/20 ms, 0 underruns. Play alongside other apps Off (the default): MainActivity takes audio focus (AUDIOFOCUS_GAIN, USAGE_GAME) on start/resume and gives it back on pause, so other apps' music pauses; On: no request. The AAudio stream is tagged USAGE_GAME (`N64_AUDIO_USAGE=0` drops the tag; Thor device latency is the same either way, 90-99 ms on its shared, non-RAW path). Time stretch isn't built: see the README item. Dev: `--es env N64_SLOW_PCT=<n>` caps the game at n% of full speed

## Conventions
- Core options are overridden in `g_optionOverrides` (libretro_host.cpp); M3 replaces this with the profile DB.
- Per-game facts live in `gamedb/games.json` (rules: `gamedb/README.md`): any change to a game's status (problem found, fixed, regressed, game-specific setting added or dropped) updates it in the same commit.
- Emulation runs on one native thread that owns the GL context; UI thread only posts surface/input changes.
- License: GPL-3.0-or-later (`LICENSE`; README "Licensing" says why). GPLv3 code may be copied, GPLv2-only code (Project64) may not. ares-derived code keeps its ISC notice.
- M0 verified on AYN Thor (SD 8 Gen 2): SM64 at 60 fps on GLideN64. `adb logcat -s joey64host` prints fps stats every 5 s.

## Known issues
- parallel-RDP on AYN Thor with the stock Adreno 740 driver (676.53): black screen, the compiler fails on a parallel-RDP compute shader. Fixed by Turnip ("Turnip Gen8 V38", Mesa 26.99.99 / Vulkan 1.4.363): renders correctly at 60 fps.
- Synchronous parallel-RDP (needed for CPU framebuffer reads, e.g. Snap photos) costs ~10 ms/frame in Snap on the Thor (async: ~2–4 ms; GLideN64: 2.5 ms). On Adreno/Turnip, parallel-RDP runs synchronous by default (`MainActivity`): async there breaks Yoshi's Story, Resident Evil 2, Cruis'n USA (black), New Tetris (halts) and Snap, also in upstream's async code, while sync costs ~1-2 ms and no fps on the Odin 3/Duo. On Mali (Flip) sync costs up to a third of the frame rate, so it stays async except games in `kSyncRdpGames` (libretro_host.cpp, by header game code: Snap = NPF). Synchronous only outside fast-forward. `--es opts mupen64plus-parallel-rdp-synchronous=True|False` overrides.
- Smart parallel-RDP sync (core `gliden64-update`): stands in for synchronous mode (`--es env N64_RDP_SMART=0` gives plain sync). parallel-RDP runs async, remembers the RDRAM pages it drew into, and at each SyncFull mprotects them; the first CPU access faults, waits for the GPU and unlocks them (gopher64's idea, done with page protection). Neither the Duo's Turnip nor the Flip's Mali has VK_EXT_external_memory_host, so parallel-RDP copies results back on a worker thread; the core maps RDRAM from a memfd twice and gives parallel-RDP the second, never-protected view (`g_rdram_alias`). Measured: Duo renders RE2 and Cruis'n USA like sync (async shows them black) at or below sync cost; Flip Snap 14.4 -> 5.0 ms/frame vs sync. Most games touch drawn pages every frame (Flip: SM64 587, OoT 599 waits per 600 SyncFulls), so it is no faster than sync for them; on by default everywhere it cost the Flip ~20 fps in SM64/OoT/Banjo against async, so Mali stays async except `kSyncRdpGames`. The log line `smart sync: N CPU waits in the last 600 SyncFulls` shows how often a game reads back what the RDP drew. Precise mode (default since core 92fe5c3, `N64_RDP_SMART_PRECISE=0` turns it off) also tracks the drawn byte ranges: a dynarec load/store (PC in new_dynarec's code cache) whose 8 bytes miss them opens only its page without waiting, and a helper thread relocks it 0.5 ms later; copies (DMA, RSP, C memcpy) always wait, since they fault only on their first byte (letting them through left Cruis'n USA stuck). Portal +11.9% over page-level smart sync, Duo compat 82/82. `N64_RDP_SMART_DEBUG=1` logs inside / copy / shared-page fault counts
- Early acquire on Mali (default since 2026-11-05, MainActivity sets `N64_EARLY_ACQUIRE=30` unless `--es env` does): with repeat frames skipped, after 30 new frames in a row the next frame acquires its swapchain image at frame start, so a blocking acquire waits before the input poll (Flip Smash poll->display 58 -> ~40 ms). Off on Adreno: no gain on the Duo, Odin 3 or Portal, GoldenEye judders on the Duo. Flip compat 82/82
- Single-threaded RDP commands on Mali (default since 2026-11-06, MainActivity sets `PARALLEL_RDP_SINGLE_THREADED_COMMAND=1` unless `--es env` does): parallel-RDP processes commands on the emulation thread, not a worker ring. Flip +3.7% uncapped, none slower, compat 82/82. Adreno keeps the ring (Duo mixed)
- Recompiler compile thread on Mali only (2026-11-08, Joey: "your call"; core `dd-drc` / `drc-tier`, MainActivity sets `N64_DRC_THREAD=1` on Mali unless `--es env` does): new RDRAM code runs in the interpreter while one worker compiles it from a snapshot; a compile the emulation thread must wait for (TLB-mapped code and the like) runs on it. Flip MK64 race start worst frame 88-90 -> 45 ms, -0.4% uncapped; Adreno keeps it off (no hitches there, Odin 3 worst frames worse). The core logs `dynarec: compiling on its own thread` when it is on
- Lazy waking of the RDP command worker on Adreno only (Joey 2026-11-07; the core has it on unless `N64_RDP_RING_LAZY=0`, MainActivity sets 0 on every non-Adreno GPU unless `--es env` does): the writer wakes a sleeping worker only at 1024 queued words or when the work must run soon, and after a real wait it wakes eagerly for a while (`N64_RDP_RING_ADAPT=0` turns that part off). Portal +4.4% uncapped, Duo +3.0%, compat 82/82 on both. The core logs `Command ring: lazy waking on/off` at start (Granite info level: hidden on the Duo)
- KGSL GPU priority 1 on the Odin 3 (default since 2026-11-07, Joey's decision; MainActivity sets `N64_KGSL_PRIO=1` by `Build.MODEL` before the driver loads, unless `--es env` does; `N64_KGSL_PRIO=` empty turns it off): a hook in libadrenotools' namespace (`kgsl_priority_hook.c`) sets the priority on each KGSL context the bundled Turnip creates (it asks for none). - No parallel-RDP pipeline pre-build on Adreno (default since 2026-11-07, Joey's decision; MainActivity sets `N64_RDP_PREBUILD=0` when the GPU name has Adreno, unless `--es env` does; `N64_RDP_PREBUILD=1` turns it back on). Why: on a cold driver cache the pre-build stalled ~0.6 s at start on the Portal (`portal-pbfirst`), compiling on demand 63-170 ms; warm launches wait 0 ms either way. Mali (Flip) keeps it.
- Repeat frames (default since core 92fe5c3 / app 07869ad): the core skips scanning out a refresh when the VI registers match, the RDP drew nothing into the scanned rows and their RDRAM hash matches; the Vulkan side then acquires and presents nothing for it. Portal +21.5%, Flip +14.7% uncapped. `N64_RDP_SKIP_DUP=0` (core) and `N64_SKIP_DUPES=0` (app) turn it off; `N64_RDP_SKIP_DUP_DEBUG=1` logs the detection
- CPU core: the dynamic recompiler for every game since 51efc5f (2026-11-09). Jump cache (core jcache-sp c0a3963, bundled 2026-11-09): a 4096-entry guest address -> compiled code table in front of the hash table, on for Adreno, off on every other GPU (`GpuRules.settings` sets `N64_DRC_JCACHE=0`: the Flip lost Conker -5.8%, GoldenEye -9.6%); Duo compat 82/82. Sin and Punishment (English patch), the last game on the cached interpreter, runs on it since core 19eff8c (sp-dynarec), which compiles code in cartridge ROM.
- ROM hacks that DMA from odd cartridge addresses (SM64 Last Impact: MIO0 data one byte off, then the decompressor overwrites its own code; Star Road Deluxe: collision data one byte off, NULL pointer) crash in every upstream libretro build: hardware and upstream ignore bit 0 of the PI cart address. The core (joey64-core `gliden64-update`) now follows M64Plus FZ: ROMs missing from mupen64plus.ini keep bit 0, ROMs in it align unless their entry says `ForceAlignmentOfPiDma=0` (FZ's six SM64-hack entries copied). Both run on parallel-RDP (Odin 3 60 fps; Flip: Last Impact 60, Star Road 35-40 in-game)
- ROMs missing from mupen64plus.ini (hacks, randomizers, translations) take their save type from the header game ID (core `rom.c`, lists from ares, ISC); before, they all got EEPROM 4K, so hacks of 16K EEPROM games (DK64, Banjo-Tooie, Yoshi's Story) could not save. SRAM/FlashRAM were already auto-detected by the cart on first access
- Display lag: the core used to scan out (and end the libretro frame) at the VI interrupt, before the game's handler set the new VI_ORIGIN, so every frame was shown one frame late. It now scans out at the active picture start (`VI_SCANOUT_EVT`, about 1 ms after the origin write on SM64/MK64/OoT instead of 17 ms): ~16 ms less lag, same speed. `--es env N64_SCANOUT_AT_VI=1` restores the old timing

Rate control (max 1%) holds the fill at the target when vsync paces instead, and stays neutral while audio paces. The stats line shows fill/target, underruns and `poll->display` (input poll to scanout, from VK_GOOGLE_display_timing). - 120 Hz panels (Portal, Duo, Odin 3) with 60 fps games: by default each frame is presented once, as soon as it's ready (like RetroArch's default), so 5-19% of frames show for 1 or 3 refreshes instead of 2 (Odin 3 at 4x: ~90%). `--es env N64_SWAP_INTERVAL=1` presents each frame twice (RetroArch's swap interval 2): no judder, +8-16 ms poll->display. `N64_SWAP_INTERVAL=2` is timed pacing (`VkContext::paceFrame`): one present per frame with a `desiredPresentTime` on an even vsync, frames started just in time; 0-5% uneven for +2-7 ms (Portal ~20 -> ~24 ms, Duo ~23 -> ~27-33 ms, Odin 3 ~20 -> ~23 ms). - The activity handles every config change itself (`configChanges` in the manifest), so dark mode, font size, dock or keyboard changes no longer restart the game (verified on the Duo: same process through a dark-mode and font-scale flip). Also `appCategory="game"` and `preferMinimalPostProcessing`
- Benchmarking (dev env): `N64_BENCH=1` runs uncapped (no speed cap, vsync off, audio dropped, settings unchanged; repeat frames are still skipped unless `N64_SKIP_DUPES=0`), so the counter shows the headroom a full-speed game has; `N64_STATE=<raw save state path>` loads a state 30 frames after boot.
