# Joey64

Standalone Android N64 emulator built on the **mupen64plus-next** libretro core,
focused on handheld devices (Retroid, Odin, AYN, Anbernic).

## Status
Runs games on real handhelds (Retroid Pocket 3.5 Flip, Odin 2 Portal, Retroid Pocket Duo, Odin 3)
with parallel-RDP on Vulkan (bundled Turnip on Adreno) or GLideN64. No menus yet: games are started
over adb (see CLAUDE.md).

## Layout
```
app/src/main/java/.../MainActivity.kt   Surface + lifecycle, picks core/ROM
app/src/main/java/.../NativeBridge.kt   JNI bindings
app/src/main/cpp/libretro_host.cpp      dlopen core, environment callbacks, run loop
app/src/main/cpp/egl_context.cpp/.h     EGL/GLES3 context + FBO for the core
app/src/main/cpp/audio_out.cpp/.h       AAudio output
app/src/main/cpp/libretro.h             Download from libretro/libretro-common (see below)
```

## Getting the core
Build our core, Joey64 (the private repo JoeysRetroHandhelds/joey64-core, a fork of
https://github.com/libretro/mupen64plus-libretro-nx), then run `devtools/bundle-core.sh`: it copies it to
`app/src/main/jniLibs/arm64-v8a/libjoey64_libretro_android.so` and records the core commit in `core-version.txt`.

Copy `libretro.h` from https://github.com/libretro/libretro-common/blob/master/include/libretro.h
into `app/src/main/cpp/`.

## Roadmap
Focus now: performance, compatibility and latency; menus come after.

- [x] M0 – Host core, load ROM, GLES video, AAudio, run loop
- [x] M1 – Input: positional gamepad mapping, analog sticks, fast-forward (unbatched input on Android 11 still open)
- [x] M2 – Vulkan HW context for parallel-RDP, Turnip/system driver pick per GPU
- [ ] M3 – Per-game / per-GPU profile DB (ROM hash + GPU vendor/driver → renderer + core options); a few rules are hard-coded so far
- [~] M4 – Frame pacing: big-core pinning, audio sync, low-latency audio, timed pacing on 120 Hz (opt-in) done; speed cap when audio doesn't pace done too (app c642e3e: New Tetris 60 fps on 120 Hz, was 121); thermal fallback open
- [ ] M5 – Handheld frontend: game list, settings, controller profiles, controller-only UI
- [ ] M6 – Test harness: compatibility runs across a ROM library per device (scripted, first pass done), n64-systemtest results, Pokémon Snap photo check. n64-systemtest crashes the core first (dynarec: "Compile at bogus memory address b0001040" on code run from cart ROM; the cached interpreter crashes elsewhere): fix that before using its results
- [ ] Paks: Controller Pak works (player 1, saved in the .srm). Rumble Pak works too (app c642e3e; 33 ms pulses in Star Fox 64), still to do: pick memory or rumble pak per game, Transfer Pak (Game Boy ROM + save for Pokémon Stadium 1/2), paks for players 2-4
- [ ] Save states, then run-ahead (removes games' built-in input lag). Started: dev-only loading (`N64_STATE=<raw file>`, 30 frames after boot, for benchmarks); no saving, slots or UI yet. RetroArch states import cleanly once unpacked: RZIP (zlib chunks) around a RASTATE container whose MEM chunk is the core's `M64+SAVE` data; Joey's states from RetroArch's Mupen64Plus-Next load in our core (OoT and SM64 checked so far; the benchmark logs each load). So the app can read RetroArch .state files directly Then the lag test from docs/latency-plan.md (from a state, run K frames with and without a press; the first frame that differs is the game's own lag) to set run-ahead per game in the profile DB.
- [x] Performance on weak devices: parallel-RDP command-ring syscalls, NEON RSP vector path (core ce55255, 00044b7, 6be4035)

So in a slow run the thread spends about 1 ms more per frame not running, inside the core's frame (no smart-sync waits: 0 in both): waiting for something, or runnable but not given the CPU (another thread on cpu7). Scheduler check (2026-11-05, `schedmon.sh` beside `duo-sched`: uncapped GoldenEye, Snap, Paper Mario x 4, every app thread's run time, time waiting for a free CPU, CPU and context switches each second): both levels showed again (GoldenEye 359-363 / 261-262, Snap 727-730 / 478-479, Paper Mario 399 / 325-326). It is not CPU contention: the emulation thread stays on cpu7 and waits for a free CPU only 2.6-3.5% of the time in fast and slow runs alike, with the same involuntary switches (35-54/s). It sleeps by itself: Snap runs 69-70% of the time when fast and 50% when slow, GoldenEye 86% / 66%, Paper Mario 89% / 74-75%, about one voluntary sleep per frame in both. So a slow run spends ~0.7-1 ms more per frame blocked on something, most likely the GPU side (scanout waits for parallel-RDP's work, or submission latency: GPU execution time per frame is the same in both levels, item 32), which would also fit GPU priority 1 keeping these games on the fast level (`duo-prio2`). Next: the same games with parallel-RDP's scanout wait stats (`N64_RDP_WAITSTATS=1`), queued after the merged-core run (`chain53_duo_waits2.sh`) (Duo low priority)
